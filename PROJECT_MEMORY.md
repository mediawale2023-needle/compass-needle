# Project Memory

This file is the persistent working memory for Compass Needle. Read it before making code changes.

## How To Use

- Update this file when a decision, rule, or project insight is likely to matter again.
- Keep entries short, concrete, and durable.
- Do not use this file for temporary scratch notes; put those in `TASK_LOG.md` or the active discussion.

## Current Operating Protocol

- Read `AGENTS.md`, this file, and `TASK_LOG.md` before making code changes.
- Share a pre-change summary with the user and wait for confirmation before editing code.
- After every completed change, update this file if the change introduced durable knowledge.
- After every GitHub push, make sure `TASK_LOG.md` reflects what was pushed and update this file if the push captured a durable project decision.
- Treat seat-generic, tenant-safe architecture as the default standard for every new change. Do not hardcode behavior, data flows, or UI assumptions to one constituency or one tenant unless it is a clearly isolated temporary bootstrap fallback that is documented as such.

## Architecture Memory

- Backend API lives at repo root with FastAPI entrypoints in `main.py`, `api_router.py`, and `admin_api.py`.
- MP frontend lives in `frontend/` and admin frontend lives in `admin/`, both using Next.js 15 and React 19.
- The platform is multi-tenant. Every data access path must preserve `tenant_id` isolation.
- Production source of truth is AWS EC2 for backend/Postgres and Vercel for both frontends.
- The canonical production backend hostname is `https://api.theneedle.in`; EC2 Caddy, MP/Admin Vercel `NEXT_PUBLIC_API_URL`, GitHub Actions backend health checks, Meta webhook callback URLs, and operator docs should use this instead of the old `backend.coinmedia.co.in` hostname.
- EC2 Caddy uses a bind-mounted `/opt/compass-needle/Caddyfile`; deployment must force-recreate the Caddy container after installing that file, otherwise the running container can keep the old mounted config even though the host file is correct.
- Production Postgres backup is now a repo-owned EC2 concern rather than a verbal checklist item: `deploy/ec2/backup_postgres_to_s3.sh` performs the nightly `pg_dump` + gzip + S3 upload from the Docker `postgres` service using `/opt/compass-needle/backup.env`, `deploy/ec2/install_backup_cron.sh` installs the host cron, and `deploy/ec2/restore_postgres_backup.sh` is the paired restore-drill path. Future backup changes should preserve the off-box S3 target and a rehearsable restore command, not just add more manual `pg_dump` notes.
- Primary account identity is now split across `tenants.tenant_type` and `users.role`: new top-level customer accounts are created with `role='owner'` and a `tenant_type` of `mp`, `mla`, or `aspirant`, while older `role='mp'` tenants remain supported for backward compatibility.
- Auth payloads now expose `tenant_type` to the MP frontend, and primary-account checks should treat both `owner` and legacy `mp` roles as equivalent until the full migration is complete.
- The MP frontend now centralizes account/session interpretation in `frontend/lib/account.js`; new UI gating and account labels should reuse those helpers instead of re-implementing role checks inline.
- Session payloads from `/api/auth/login` and `/api/auth/me` now include `tenant_type`, `is_primary_account`, and `account_label`, which are the preferred frontend contract for account-aware behavior.
- Feature locking is now tenant-type-aware: aspirant accounts must be blocked from `Sansad AI` and `Convergence` in both frontend navigation/routes and backend API handlers, while core modules like Briefcase, Letterbox, Drafter, and Schemes remain available.
- `frontend/lib/account.js` now owns the feature-level access helpers (`canAccessSansadAI`, `canAccessConvergence`); use those instead of broad “MP-only” role checks when adding or editing gated UI.
- Primary-account identity has now been normalized further into two axes on `tenants`: `account_stage` (`aspirant` or `elected`) and `seat_type` (`mp` or `mla`). Keep `users.role` for permissions (`owner`, `staff`, `admin`) and treat legacy `tenant_type` as a backward-compatibility shim rather than the future source of truth.
- Shared geography is now seat-scoped rather than tenant-scoped. Persist base geography rows once per seat using keys like `mp:<seat>/<assembly>` or `mla:<seat>/<assembly>`, allow multiple tenants to reference the same seat, and keep only generated `geo_override` / `geo_alias` rows tenant-specific.
- Same-seat rivals are now a supported model: multiple aspirants and an elected office can share one constituency/seat safely as long as tenant-owned data remains filtered by `tenant_id` and any geography/bootstrap helper uses `tenant_id -> seat` instead of `seat -> tenant_id`.
- The admin geography workflow is now seat-aware at the UI layer too: `admin/app/dashboard/geography/page.js` lets operators choose `MP Seat` vs `MLA Seat`, stores shared geography through the existing global admin routes using `seat_type` query parameters, and shows saved geography grouped by seat rather than assuming every record is a Lok Sabha constituency.
- The launch-readiness `Configure geography` action now routes to the dedicated geography page with `tenant_id` context. In tenant-aware mode, the geography page should prefill the account seat, offer a first-class `reuse existing shared seat geography` path for rival/same-seat accounts, and only fall back to PDF upload when no suitable shared seat geography exists yet.
- Admin overview and geography/rules copy should now prefer `account`, `tenant`, and `seat` language over `MP`-only phrasing unless a page is truly parliamentary-only.
- Shared seat geography fan-out is now covered by backend tests: `auto_generate_overrides()` must create separate `geo_override` rows for every tenant on the same seat without leaking MLA-seat geography into MP-seat tenants.
- Admin staff management must never treat primary political accounts as ordinary staff. `owner` and legacy `mp` users are now excluded from `/api/admin/staff` and blocked from staff suspend/reassign/edit flows; staff tooling is for non-primary tenant users only.
- The ORM `User` model now explicitly includes `phone`, matching the existing migration and the live staff/WhatsApp features. Future user-facing phone work should rely on the ORM field rather than assuming it exists only via raw SQL migrations.
- Updating a tenant constituency through the admin constituency endpoint must keep `users.constituency`, `tenants.constituency`, and `tenant_profiles.constituency` aligned so tenant-aware flows like geography reuse and readiness checklists do not drift across tables.
- `modules/geography_resolver.py` must keep three location-matching safeguards in place: MLA tenant assembly names should be resolved up to their parent parliamentary constituency for `scope_parliamentary` filtering, fuzzy keyword matching should stay at the narrower-but-usable `>93` threshold for Indian spelling variants, and newline-separated locality strings should seed each line independently so prefixes like `Nath Pai Circle` remain directly matchable.
- The geography resolver index is now seat-aware internally: assembly buckets are keyed by `seat_type + seat_name + assembly`, and tenant-scoped resolution should prefer the tenant's own seat context over broad parliamentary-string filtering. This avoids collisions when different seats reuse the same assembly name.
- Legacy override bulk saves in `save_overrides_to_db()` must never wipe shared geography or generated alias rows. Only `phone_mapping` and `geo_override` rows are safe to replace wholesale; `geography_data` and `geo_alias` rows are durable shared assets.
- Geography onboarding now has two tiers of validation: weak coverage remains a warning in the returned validation payload, while generated alias collisions against another assembly on the same seat are blocking errors and must stop the save. New save paths should surface `validation.blocking_errors` instead of silently accepting dangerous shared-seat ambiguity.
- WhatsApp geography decisions now persist structured `geography_diagnostics` inside `case_metadata`, including attempted resolution sources, tenant scope, match type/confidence, rejected AI assemblies, and final resolved/unresolved state. Future ops/debug tooling should read that field before inferring why a case stayed blank.
- Historical blank geography is now repairable through `scripts/backfill_case_geography.py`, which is intentionally tenant-scoped and fills blank `location` / `assembly` values from the raw message while also writing backfill diagnostics into `case_metadata`.
- The WhatsApp ingestion wrapper in `main.py` must stay signature-aligned with `modules/whatsapp_geography.finalize_geography_decision()`. A mismatch on `location_required` caused live tenant cases to save without geography even though tenant aliases and the resolver were healthy.
- The aspirant-facing UI copy direction is now `workspace`/`team` oriented rather than `MP office` oriented. High-visibility MP frontend surfaces such as Settings, schedule cards, and Briefcase triage notes should prefer labels like `Your profile`, `Workspace details`, `Role / Position`, `Team`, and `Constituency Workspace` when the copy does not need to imply elected authority.
- A second UI-only wording pass extended that same direction into fallback labels and helper text: avoid defaults like `MP`, `Member`, `PA / Staff`, or `MP Office` on shared workspace screens unless the feature is specifically parliamentary or elected-office only.

## Safety Rules Worth Rechecking

- Never bypass JWT, bcrypt-only auth, webhook signature validation, rate limits, or tenant scoping.
- Never build raw SQL from user input. Use bound parameters.
- Never expose raw internal errors in API responses.
- Treat WhatsApp, AI classification, and case query flows as high-impact surfaces because regressions are user-visible quickly.

## Fragile Or High-Risk Areas

- `main.py`: startup behavior, webhook handling, and background worker wiring can affect ingestion reliability.
- `api_router.py` and `admin_api.py`: large surface areas with auth and tenant-isolation risk.
- `sansadx_backend/db.py`: model changes can ripple into multiple dashboards and workflows.
- `modules/case_query_*`: natural-language query parsing and formatting are tightly coupled to live WhatsApp usage.
- `modules/whatsapp.py`: outbound messaging issues are operationally sensitive.

For older or partially enriched cases, the drawer must fall back to canonical case fields like `problem_domain`, `problem_subdomain`, `detected_language`, and a structured summary derived from saved taxonomy/location metadata instead of echoing the raw citizen message as the “summary”.
- The Briefcase case-detail surface is now moving toward the `Compass Needle Design System-4` structure: a wider split modal with a left reading/notes column and a right `Case file` rail. When restyling this surface, keep the existing live behaviors intact — thread-case switching, per-complaint resolve, geography save/lock, activity fetch, and response drafting must remain behavior-first under the new visual shell.
- Briefcase no longer supports the old officer/escalation workflow. The MP frontend should not surface `Escalate to Officer`, the MP API should not expose `/api/officers` or `/api/escalations`, and legacy case status `escalated` should be normalized to `in_progress` at startup so removed UI states do not linger after deploy.
- Live Playwright sessions live only in backend process memory (max 3 on the shared EC2 host). Aborted Escalates still count against that cap. Staff must be able to see this office's open sessions in the Briefcase Government Portal section and End / End all them (`GET /api/govt/sessions`, `POST /api/govt/sessions/{id}/close`, `POST /api/govt/sessions/close-all`). List and close are tenant-scoped; the concurrency cap is global.
- Briefcase Escalate calls `POST /govt/session/start` (Playwright) or `POST /govt/translate` (Gemini). The shared frontend API client must not use the 8s dashboard timeout for those paths — session start needs ~120s and must not retry on abort, or Safari reports `Fetch is aborted` and staff see a no-op. Until `GET /api/govt-portal` returns, treat live automation as on (the backend default); defaulting it off routed Escalate into translate and hit the same abort.
- In the Briefcase case drawer, `Escalate` is the only control that starts government-portal filing (live session, or worksheet-only if live automation is off). Do not put `Open live portal`, `Worksheet only` / `Prepare worksheet`, or an external portal-file link in the Government Portal section — those duplicate Escalate. Keep the worksheet copy fields and `Mark as submitted` so staff can record the portal reference after filing. `Escalate` belongs on every unfiled complaint: thread rows for multi-complaint cases, and the sticky footer next to Mark resolved (including single-complaint cases).
- Clicking Escalate / preparing a govt worksheet must not bump `cases.updated_at`. Briefcase All cases `Newest first` must order by `created_at` (received date), including after contact-thread grouping — last staff touch must not jump old rows. Use the `Recently updated` sort when last-touched order is wanted. Only marking a portal reference as submitted should change Briefcase status, and then to `in_progress`.
- A live government-portal session may start only while there is no recorded portal reference and `govt_status` is still `not_forwarded` or `pending_staff_submit`. Once a reference exists, or status is `submitted` / `under_review` / `escalated` / `resolved` / `rejected`, `POST /govt/session/start` must 409 and Briefcase must hide Escalate. Submit of the same reference is a no-op; a different reference must 409 and must not overwrite the stored number.
- **Live govt-portal sessions never auto-fill grievance fields — this is a deliberate, standing product decision, not a gap to fill in later.** `modules/govt_sync/browser_session.py` has no `_autofill` function; it never existed as dead code to re-enable, it was fully removed. Escalate opens the real portal, streams it into Briefcase, and — if `field_schema.post_login_entry_path` is configured for that portal — auto-navigates to the grievance form once staff finish logging in. Every field on that form, including department/subject/description, is typed by the staff member themselves; the AI worksheet (`GovtSyncCopyField` rows) is shown alongside purely as copy-paste reference text. `GOVT_LIVE_AUTOMATION_ENABLED` (default `true`, checked fresh per-request in `_govt_live_automation_enabled()`) is kept only as an emergency off switch for the open+navigate step itself — flip to `false` without a redeploy if a specific portal ever blocks/rate-limits the shared EC2 IP (every live session runs from one IP across every tenant and state, and the automation is fingerprintable regardless of IP; no state portal's ToS for this has been verified). While off, Escalate falls back to the AI worksheet only (`handlePrepare`). The filer-identity (MP's name in citizen/filer fields) and AI-description PII-scrub questions remain open, unrelated to this switch, and unaffected by removing autofill (the worksheet text staff copy from is still AI-generated either way) — do not resolve those without the user's explicit direction.
- `active: true` on a `govt_portals` row means the URL/identity is confirmed, not that the portal is actually usable — `department_taxonomy` is a separate gate, and an empty one fails `_prepare_govt_worksheet` closed with a 400/warning by design rather than guessing a department. As of 2026-08-20, Rajasthan/UP/Karnataka/Maharashtra/Bihar/Madhya Pradesh/Mizoram/Odisha/Punjab/Tamil Nadu/Tripura all have a best-effort taxonomy mapped (`field_schema.taxonomy_verified` still `false` for every one of them — none confirmed against a live post-login department dropdown yet). Only Uttarakhand is still `active: true` with `department_taxonomy: {}`, pending its separate TLS reachability question below.
- `govt_portals.live_session_supported` (default `true`) is a third, independent gate alongside `active`/`department_taxonomy` — it means "a live Playwright session can actually reach this portal from our EC2 host," not a research-confidence or ops toggle. Set to `false` only after confirming a real network-level failure (see Maharashtra, 2026-08-19: TCP connect times out on both ports 80/443 from EC2 specifically — DNS resolves, the same host connects instantly from anywhere else — most likely the portal blocking our EC2/AWS IP range). Diagnose with `.github/workflows/diagnose-portal-reachability.yml` (curls a hostname from both the EC2 host and inside the backend container) before assuming a portal's live session "should" work — this must happen BEFORE spending research time on department-taxonomy mapping, not after (Maharashtra's taxonomy work would have been wasted if done first). When `false`: `POST /govt/session/start` 403s server-side regardless of `GOVT_LIVE_AUTOMATION_ENABLED`, and Briefcase's Escalate opens `GET /api/govt-portal`'s `entry_url` in a new browser tab (the staff's own network) plus the AI worksheet in Needle, instead of attempting a session that would just time out.
- The 2026-08-19 reachability sweep (Rajasthan, UP, Maharashtra, Bihar, Madhya Pradesh, Mizoram, Odisha, Punjab, Tamil Nadu, Tripura, Uttarakhand) found Maharashtra was the outlier, not the norm — every other state connects cleanly. Uttarakhand is a distinct, still-open case: TCP connects fine on port 443, but the TLS handshake fails with `SSL routines: unsafe legacy renegotiation disabled` (curl/OpenSSL 3.0 strictness against an apparently old/misconfigured server-side TLS setup) — this is NOT the same "silently dropped packets" signature as Maharashtra's IP block, so `live_session_supported` was deliberately left untouched (not set to `false`) pending an actual Playwright test, since Chromium's TLS stack (BoringSSL) may negotiate this differently than curl+OpenSSL did. Do not assume Uttarakhand is blocked like Maharashtra without that test, and do not assume it works either.
- Department-taxonomy confidence is not uniform across the 2026-08-20 batch — `source_note` on each portal spells out exactly which department names were directly confirmed by the source used (Wikipedia "Government of X" pages) vs. inferred from standard Indian-state naming conventions (mainly the water-supply/PHE department, which general cabinet-portfolio listings don't always break out separately). Tripura is the least confident of the 8 now-configured states: 3 of its 9 mapped categories (Infrastructure & Utilities' Urban Development half, Housing & Land, Education's School Education half) are inferred, not confirmed — prioritize it first if this state ever gets a real tenant and someone can check the live post-login dropdown.
- As of 2026-08-22, `status_check_url`/`status_check_mode` on a `govt_portals` row are vestigial for any portal whose real status page turns out to be a client-side-rendered SPA — plain `requests.get()` + BeautifulSoup can never see the actual status data there, regardless of how the keyword-scrape logic is tuned. Rajasthan Sampark was the first confirmed case (its `Admin/Grievance_Status.aspx` page renders entirely via React). The fix is a new `govt_portals.status_check_adapter` column: when set, `modules/govt_sync/adapters/__init__.py`'s `get_adapter()` dispatches to a dedicated adapter keyed off that string instead of the generic `portal_type` → `ManualAssistedAdapter` path, before ever looking at `status_check_url`. `modules/govt_sync/adapters/rajasthan_sampark.py` (`status_check_adapter: "rajasthan_sampark_api"`) calls Rajasthan Sampark's real backend gateway (`POST /gateway/api/GatewayService/GetList`, a single generic JSON-RPC-style endpoint keyed by `Module`/`Path`) directly with `requests` — no browser needed for status checks, only for filing (which stays a human on the live portal, unchanged).
- Rajasthan Sampark's OTP verification is scoped to the mobile number, not per-grievance or per-session — confirmed valid for at least ~28 minutes across multiple grievances on the same mobile (true expiry beyond that untested). This is why `govt_otp_sessions` caches one verified session per `(tenant_id, portal_id)` rather than per-case: staff verify once via Settings → Government Portal (`POST /api/govt/otp/send` then `/verify`), and every pending case on that portal can then be polled silently until the cached session goes stale (`last_check_failed=true`, surfaced as `needs_verification` from both `POST /cases/{id}/govt/poll` and the background poller, which skips the rest of that tenant+portal's pending cases for the rest of the run once one comes back needing re-verification, rather than re-failing identically per case). The adapter deliberately never extracts the complainant PII block the gateway also returns (name/mobile/email/address) — only status/department/subject/dates are read into `StatusResult`.
- Two real, unauthenticated Rajasthan Sampark backend endpoints were found during this investigation (`GetDetailByGrievanceNo` returns a citizen's unmasked mobile from just a grievance number; `GetActionIntegratedHistoryListCitizen` returns full grievance history from a guessable sequential ID) — neither is used by Needle's adapter, and both are earmarked for a separate, responsible disclosure to RISL, not something to exploit or build on further.
- As of 2026-08-22, the mobile-scoped-OTP session machinery is a reusable framework, not Rajasthan-specific code — do not re-inline it into a future state's adapter. `modules/govt_sync/otp_sessions.py` is the plain `govt_otp_sessions` DB layer (get/upsert/mark-failed/touch-used/verification_state, zero portal knowledge). `OtpGatedStatusMixin` (`modules/govt_sync/adapters/base.py`) is the orchestration layer: mix it into a concrete adapter ahead of `ManualAssistedAdapter` (mixin first, so its `check_status()` wins in MRO — `class XAdapter(OtpGatedStatusMixin, ManualAssistedAdapter)`) and implement only three hooks — `_send_otp`/`_validate_otp`/`_fetch_status` — to get `start_verification`/`complete_verification`/`verification_state`/`check_status` for free as instance methods. `_fetch_status()` can return either a single `raw_status_text` or `status_text`+`sub_status_text` — whichever shape fits that portal's real response. `rajasthan_sampark.py` is now just the three Sampark-specific hook implementations plus its gateway-envelope calling convention — nothing else. `api_router.py`'s `/govt/otp/send`, `/govt/otp/verify`, and `_govt_otp_verification_state` dispatch generically via `get_adapter(portal)` + `hasattr()`, with zero hardcoded per-portal imports — a second OTP-gated state needs only a new adapter module + one `_STATUS_CHECK_ADAPTERS` registration in `modules/govt_sync/adapters/__init__.py`, whose module docstring spells out the 3-step process (trace real traffic first, never assume; implement the mixin's hooks only if it turns out to be mobile-scoped-OTP-gated like Rajasthan; otherwise implement `check_status()` directly instead of force-fitting a different auth shape into this mixin).
- **Reference architecture for status-check adapters (as of 2026-08-22)** — a 3-axis taxonomy that applies ONLY to `check_status()`; Filing (`prepare_submission`) is unaffected and stays staff-driven/live-browser for every portal regardless:
  ```
  GovtPortalAdapter
  ├── Filing — staff-driven / existing live-browser workflow
  └── Status Check
        ├── Execution: Manual | Automated HTTP
        ├── Authentication: None | Mobile OTP | Grievance OTP | Account | Static credential | Other/Unknown
        └── Human verification: None | CAPTCHA | Other/Unknown
  ```
  Authentication and Human verification are **independent axes** — CAPTCHA is never a child of Authentication. A portal can legitimately combine Automated HTTP + Mobile OTP + CAPTCHA all at once (this is exactly what UP Jansunwai's real tracker, `jansunwai.up.nic.in/ComplaintTracker`, appears to need: reference number + mobile + OTP *and* a separate CAPTCHA field on one form — a taxonomy that can't represent "both at once" can't represent UP). Execution is also independent of a portal's inherent auth model: it describes **Needle's own current integration status**, not what the portal technically supports — two portals can both be Mobile OTP + no CAPTCHA while one is Automated HTTP (Rajasthan, because the work was done) and the other stays Manual (because nobody has done it yet); never read "Manual" as a claim about the portal. **"Unknown" is a valid, first-class classification** — never infer an authentication model from a login button's mere existence, or from another state's behavior just because both ask for "mobile + OTP." `govt_portals.status_check_adapter` configured means Execution=Automated HTTP (a real implementation exists); absent means the `ManualAssistedAdapter` fallback applies. Known naming drift, not a bug: `ManualAssistedAdapter` currently covers two cells of this taxonomy at once (true Manual for `login_required` portals, and Automated HTTP + None + None for `status_check_mode=public_reference` portals like CPGRAMS's plain scrape) — not worth splitting until a second portal actually needs that distinction in code. Full detail (including the current per-state classification table and the 10-step next-state investigation procedure) lives in `modules/govt_sync/adapters/__init__.py`'s module docstring — that is the canonical source, this bullet is a pointer to it.
  - Current classification (confirmed only; everything else is Unknown, never guessed): **Rajasthan Sampark** = Automated HTTP / Mobile OTP / None (implemented, the proven OtpGatedStatusMixin reference). **Karnataka iPGRS** = Automated HTTP / None (no persisted session — see below) / CAPTCHA (implemented 2026-08-24, the proven InteractiveStatusCheckMixin reference). **CPGRAMS** = Automated HTTP (scrape) / None / Unknown (only the search form was checked, never a real result page). **UP Jansunwai** = Manual / OTP-present-but-scope-Unknown / CAPTCHA (not implemented). **The other 8 remaining `login_required` states** = Manual / Unknown / Unknown — do NOT classify them as "Account" auth just because login is required; that column only means staff log in somewhere, not what the backend actually enforces.
  - Do not pre-build abstractions for hypothetical portals (no Grievance-OTP mixin, no Account-auth abstraction, no Browser-driven-status-execution abstraction) until a real portal requires one — CAPTCHA no longer belongs on that "don't pre-build" list, see the `InteractiveStatusCheckMixin` bullet below. The discipline that produced `OtpGatedStatusMixin` (see above) is: investigate a real portal → implement that real case directly in its own adapter → only once a *second* real portal repeats the same pattern, extract the shared piece. Never skip ahead to the abstraction.
- **`InteractiveStatusCheckMixin`** (`modules/govt_sync/adapters/status_flow.py`, merged 2026-08-22, first real adapter 2026-08-24) is the second reusable status-check mechanism, deliberately never merged with `OtpGatedStatusMixin` — they solve genuinely different problems. `OtpGatedStatusMixin` = verify once out of band, cache the session (`govt_otp_sessions`), reuse it for many later automated checks (Rajasthan). `InteractiveStatusCheckMixin` = every single lookup needs a live human (CAPTCHA and/or OTP) *at call time*, with no evidence any portal's verification is reusable across lookups — its `check_status()` always honestly returns `checked=False` (an interactive lookup cannot complete inside one synchronous call); the real flow is `start()` (opens a session, obtains the challenge) → staff answers → `advance()` (submits, parses, completes). `GovtPortalAdapter.supports_unattended_status_check` (default `True`, `False` via this mixin) is checked by `poller.py` *before* ever calling `check_status()`, so an interactive portal is structurally excluded from the unattended background poller, not caught-and-skipped via an exception. Karnataka iPGRS (`modules/govt_sync/adapters/karnataka_ipgrs.py`) is the first concrete adapter: a `requests.Session()` per attempt (not Playwright — the real request/response contract was fully confirmed by reading the portal's own un-obfuscated inline JS, so no browser automation was needed), attempts held in a process-local in-memory dict (same precedent as `browser_session.py`'s `_sessions` — explicitly not `govt_otp_sessions`, no DB table, no Redis, does not survive a backend restart by design). New endpoints: `POST /cases/{id}/govt/status-check/start` + `/{attempt_id}/advance`, and `GET /govt-portal`'s `portal.interactive_status_check` flag (distinct from `otp_verification` — a portal is never both). Maharashtra (2-stage: CAPTCHA+OTP unlocks a server-issued `cid` required by a second CAPTCHA-gated stage) is the next planned adapter — not yet built; Karnataka was deliberately built first as the simpler, single-stage case.
- Shared seat geography should now be treated as hierarchical when possible, not purely flat. Upload rows like `Teli Patil Galli Shahapur, Belagavi` or `Somawar Peth Tilakwadi, Belagavi` should infer `sub_locality + parent_locality` during sanitation/indexing, while still preserving the original `locality` string for backward compatibility. Resolver ranking must prefer the most specific unique sub-locality, return `matched_type` plus `parent_locality`, and fall back to the broader parent locality only when that is all the citizen mentioned.
- Hyphen-delimited seat geography rows such as `Teachers Colony - Khasbag` must be treated as first-class structured geography, not raw strings. Save-time sanitation in `modules/geography_resolver.py` should infer `sub_locality=Teachers Colony` and `parent_locality=Khasbag`, generate seat-scoped aliases for sub-only, parent-only, and combined mentions, and keep any fuzzy singular/plural variants strictly as match helpers rather than letting them overwrite the canonical stored display name.
- Seat geography rows may also carry fuller citizen-facing locality names only inside `building_name` while the saved `locality` column is abbreviated (`R.C Nagar`, booth codes, etc.). The resolver should promote only locality-looking `building_name` lines into alias seeds, ignore generic venue/class-room lines, and prefer the richer matched alias as `matched_value` when it is clearly more specific than the abbreviated roll label. This rule must stay generic across constituencies rather than hardcoding one locality.
- When operators save both a standalone parent locality row (for example `Shahapur`) and separate `sub_locality - parent_locality` rows beneath it (for example `Navi Galli - Shahapur`), parent-only citizen mentions must resolve to the standalone parent row first. Inherited parent aliases from sub-locality rows are still valid fallback evidence, but they should score below the explicit parent row so `parent only`, `sub only`, and `parent + sub` all behave predictably from the same seat-scoped geography dataset.
- When shared geography only has a long combined polling-roll label (for example `Gomatesh Vidya Peetha Hindwadi`) and the citizen mentions only the broader locality fragment (`Hindwadi`), the resolver should return that broader matched fragment as the display location instead of projecting the full combined label back into the case. This keeps parent-only mentions from looking like random sub-locality guesses.
- The attempted mobile-specific Briefcase layouts were reverted on 2026-05-26. The preferred responsive direction is to preserve the desktop structure and visual hierarchy on mobile as much as possible, using wrapping, narrower spacing, and stacked controls only where necessary rather than introducing separate phone-only card layouts.

## Citizen Intake Memory

- Inbound WhatsApp transport now has a first-class durable ledger in `wa_inbound_messages`. The webhook should persist each inbound payload before returning `200`, background processing should run from that ledger row, and startup/background sweeps should rescue rows stuck in `received` or stale `processing` state instead of relying on live webhook execution alone.
- WhatsApp webhook intake must not use SlowAPI request rate limits. The durable contract is HMAC validation first, then save every Meta message in the webhook payload to `wa_inbound_messages`, return `200`, and apply abuse/backpressure only after ledger persistence. Per-sender throttling belongs at ledger processing time and should mark rows `throttled` for ops review instead of rejecting Meta delivery.
- Admin System health and ops visibility should now read WhatsApp intake from `wa_inbound_messages`, not from `cases`. Operational visibility for inbound transport belongs under `admin/app/dashboard/system/whatsapp-inbound/page.js` plus `/api/admin/whatsapp/inbound*`, with failed/stale rows exposed for retry.
- WhatsApp citizen intake now follows an `ack first, clarify later` rule: even when a case is missing location or is otherwise incomplete, the first reply should stay a normal acknowledgment instead of immediately asking follow-up questions.
- Missing-location and missing-details clarification now use delayed follow-ups driven by case metadata (`clarification_follow_up_*`) and background timers/startup sweeps, rather than sending the clarification inline during the original webhook request.
- Clarification replies from the same citizen should enrich the original recent incomplete case instead of creating a second case row; the intake flow now treats recent clarification-pending cases as update targets.
- Rapid repeated citizen intake has now moved to a real sibling-case thread model. Within the 24-hour window, each distinct complaint from the same phone should be saved as its own `cases` row with its own status, geography, notes, assignment, and resolve flow, while near-duplicate follow-ups still merge into the matching case via `contact_message_events`. The shared grouping key is `case_metadata.contact_thread_id`; Briefcase groups those sibling rows into one visible thread row, shows `+N` next to the citizen phone, and lets the drawer switch between independently actionable complaints.
- Inbound WhatsApp ledger rows must be linked for every complaint-resolution path inside that thread model, not just the first raw case insert. When intake reuses an existing case (clarification, duplicate, low-information follow-up, spam-suppressed overflow) or creates a new sibling case in an active thread, `_process_incoming_message()` should still attach `wa_inbound_messages.case_id` so ops can trace every inbound message to the exact case it affected.
- Legacy metadata-only thread rows using `case_metadata.contact_thread_items` remain supported as a temporary fallback for already-open old threads and for older test fixtures, but new intake should not create fresh child complaints in that metadata structure anymore.
- The next intake-policy pass tightened that same 24-hour thread model into explicit contact states and ack rules. Contact threads escalate by distinct-issue count: `>1 = valid_multi_issue`, `6+ = high_frequency`, and `10+ = spam_suspected`, with the suppressed over-threshold messages preserved in case metadata for Briefcase review instead of silently dropped.
- The 2026-07-11 ack-policy revision replaced blanket suppression with a bounded response contract: every distinct issue earns exactly one ack (full ack for the 1st, short localized `registered as a separate issue` ack with running count for the 2nd-5th), duplicate follow-ups and low-information nudges share ONE `registered and under review` reassurance per thread per 24h window (`contact_thread_reassurance_sent_at`), and the 6th distinct issue swaps its ack for a one-time boundary notice asking for one message per issue with location (`contact_thread_boundary_notice_sent_at`). Issues 7+ and spam-suppressed 10+ stay silent; worst case is 7 outbound messages per thread per window. Citizen acks must never carry case reference numbers — that is an explicit product decision. Threads containing emergency/offensive/irrelevant cases never receive thread-level replies (`_THREAD_REPLY_PROTECTED_STATUSES` in `main.py`).
- Immediate details-request replies at ack time are only for the contextless-media lane (`category = Document / Attachment Only`). Text complaints with `status = incomplete` follow `ack first, clarify later`: generic ack immediately, details ask via the delayed clarification follow-up. A June 5 regression that interrogated text senders immediately was hidden for weeks because CI died before pytest ran.
- Contact-thread intake now has a `CASE_COMMENT` concept (2026-07-13, Phase A): messages ABOUT an existing thread rather than a new civic report — gratitude, urging for action, status inquiries, "still pending" commentary — must never become a phantom sibling case. `modules/tenant_languages.py` resolves each tenant's 3-4 communication languages (explicit `tenants.config.communication_languages` override, else a state -> languages table off `tenant_profiles.state`, else `[Hindi, Hinglish, English]` fallback), and `modules/case_comment_heuristics.py` matches tenant-language-scoped phrase buckets (tone: grateful/urging/status_inquiry/other) capped at 12 words so a real longer grievance is never hijacked. A match is logged as a `case_comment` event on the case (same `_append_contact_message_event` mechanism as `duplicate_followup`/`low_information_noise`) and answered through the existing one-per-24h reassurance lane — no case, no distinct-issue bump, no location follow-up. `main.py`'s two duplicated low-info blocks (legacy + modern thread paths) are now one `_handle_low_info_or_case_comment` helper. Staff visibility is deliberately log-only for now — no Briefcase badge — pending usage data on whether follow-ups are a real prioritization signal.
- Phase B (2026-07-13) closed the CASE_COMMENT multilingual gap: `sansadx_backend/prompts.py`'s status enum now includes `CASE_COMMENT` plus a `comment_tone` field, with an explicit prompt rule that a message naming a real new problem is classified normally even if it also sounds urgent (only pure commentary on an already-reported issue is CASE_COMMENT). `sansadx_backend/ai_engine.py`'s `_VALID_STATUSES` whitelist includes `"case_comment"` — any new status value added to the prompt schema MUST also be added there, or the model's output is silently coerced to `"pending"` and the schema change is inert. CASE_COMMENT is grouped with OFFENSIVE/IRRELEVANT: never forced into a guessed taxonomy domain, and excluded from the emergency-keyword override so a status-inquiry mentioning a hazard word in passing can't get reclassified into a new emergency case. `main.py`'s new `_handle_ai_case_comment` helper runs right after `_run_citizen_case_enrichment` in both thread paths' distinct-issue branches, before a sibling case would be created — same non-counting treatment as Phase A's heuristic layer.
- Phase C (2026-07-13) closed the media side of the same bug class: a photo/PDF arriving with no caption (or a caption that's itself just a low-info nudge like "sir"/"update") inside an active open thread is supplementary evidence for the most recent open case, not a new complaint. `main.py`'s `_handle_contextless_media_attachment` runs before the CASE_COMMENT checks in both thread paths — deliberately a plain deterministic rule, not routed through the AI classifier, since "here's a photo" doesn't need a judgment call the way ambiguous text does. It calls `_attach_media_to_case` (an existing-case sibling of `_create_raw_contact_case`'s media insert, same `meta_message_id` dedup guard) and logs a `media_evidence_attached` thread event through the same reassurance lane. **Audio is deliberately excluded**: WhatsApp's API has no caption field for voice notes (it's always `""` at the call site in `_dispatch_inbound_ledger_row`), so an empty string there is the absence of the field, not a "no caption" signal — a voice note's real content lives in its transcript (`message_body`), so audio always falls through to normal classification instead of being silently swallowed as evidence.
- `_update_contact_thread_meta`'s no-op recompute path for `distinct_issue_count` had a latent bug (fixed alongside the above): it fell back to `1 + len(contact_thread_items)`, a legacy metadata-only-thread field that the modern per-sibling-case thread model never populates, so logging ANY event (not just the new case_comment type) on a non-anchor sibling case silently reset that case's distinct_issue_count to 1. It now prefers the count already stamped on the row when present.
- The word `missing` (and other emergency keywords) in test fixtures will trip the emergency detector and its deliberate no-ack policy; fixture text for non-emergency intake tests must avoid emergency vocabulary.
- Case enrichment now persists `detected_language` into `case_metadata` (`detected_language` and legacy `language`) so UI surfaces do not have to infer citizen language from raw text on every render.
- Historical language gaps can be repaired with `scripts/backfill_case_languages.py`, which is tenant-scoped and only backfills rows whose stored language is missing or clearly a bad default-English label compared to the case text.
- Geography resolution should now use a native-first normalization pipeline rather than constituency-specific patches: generate native-script stem variants, transliterate those variants, then score against seat-scoped geography aliases. This is especially important for Indian-language location inflections such as Kannada `ಪಿರನ್ವಾಡಿನ` / `ಡೆಪೋನಲ್ಲಿ`, where locality suffix stripping must happen before final matching.
- Staff/PA WhatsApp text should now try a schedule-intake pass before the older case-query path. `main.py` must use the conservative multilingual `modules/staff_schedule_parser.py` to save only clear schedule-like staff messages into `dashboard_engagements`; ambiguous or non-schedule text must still fall back to the existing case-query flow.

## Classification Memory

- `sansadx_backend/unified_taxonomy.py` now includes a narrow high-confidence override for official-corruption complaints: if the text clearly combines bribery/corruption or payment-demand semantics with office-official context (`talathi`, `patwari`, `tehsildar`, `babu`, etc.), taxonomy normalization must force `Bureaucratic / Administrative -> Bribery/Corruption` even if the model guessed a generic infrastructure/roads label. Keep this override structural and cross-language rather than tied to one exact sentence or script.
- Taxonomy rescue logic must also protect against locality-name false positives. If the raw text clearly indicates a water outage (`water/paani/neer/neeru` plus outage cues like `illa`, `bandilla`, `nahi`, `not coming`), `sansadx_backend/unified_taxonomy.py` should force `Infrastructure & Utilities -> Water Supply` even when the model guessed something like `Teacher Availability` because the location name contained words such as `Teacher Colony`.
- Taxonomy rescue logic must also protect against venue-word false positives. If words like `school`, `college`, `hospital`, or `depot` appear only as nearby landmarks (`ke paas`, `near`, `paas`) while the actual complaint language clearly points to garbage, drainage, water, lights, or roads, `sansadx_backend/unified_taxonomy.py` should force the matching `Infrastructure & Utilities` subdomain instead of leaving the model's venue-driven `Education` or similar guess in place.
- `sansadx_backend/ai_engine.py` must not run its own parallel geography matcher over raw geography rows or override maps. AI-extracted locations may be used only as hints, and those hints must always be re-resolved through the shared `modules/geography_resolver.py` pipeline before they can populate `grievance_data.location` or `assembly_constituency`. This keeps geography behavior seat-generic and prevents drift between classifier-time mapping and final WhatsApp geography resolution.
- Emergency no-ack behavior now depends on two layers working together: `sansadx_backend/unified_taxonomy.py` performs strong rescue overrides for explicit disaster, riot/mob violence, women/child danger, health emergency, and suicide-risk text, while `modules/emergency_keywords.py` must preserve Indic-script tokens during normalization so Hindi/Kannada/etc. emergency markers still trigger the no-ack path in `main.py`. Do not reintroduce broad punctuation stripping that breaks words like `दंगा`, and keep emergency overrides narrow enough that ordinary civic complaints still receive normal acknowledgements.

If predicate civic rules identify water/drainage/garbage/road/power/FIR/bribery/emergency style complaints, the final intake `category` must be reconciled back to the civic `problem_domain` so real grievances do not get stored as no-reply media/support/other traffic.

- Geography intelligence is being redesigned from string matching to entity linking (2026-07-24, Phase 1 shipped in shadow). The gazetteer (`modules/gazetteer.py`, tables `geo_places`/`geo_place_variants`/`geo_resolution_log`/`geo_discovery_queue`) is a closed registry of place ENTITIES — identity, type, authored parent edges, per-variant provenance, candidate/verified/deprecated status. Unresolved spans cluster into `geo_discovery_queue` ranked by distinct citizens — discovery is the system's job, not staff's (the old auto-alias attempt failed because learned strings shared authority with ground truth; entity anchoring + provenance + per-variant deprecation is what makes auto-learning safe now).
