## Phase 1 implementation and security contract

- MP and Admin JWTs must contain `sub`, `tid`, `role`, `iat`, `exp`, `credential_state`. Compare tenant and role with current DB state on each authenticated request, reject suspended accounts/disabled tenants, and fail closed on unreadable revocation state. The F02 follow-up requires the credential binding: existing tokens without it must reauthenticate; there is no unsafe legacy fallback.
- Password changes/resets, staff role/reassignment/suspension, team deactivation account deletions and tenant live-state transitions write token cutoffs within the same transaction. A failed revocation rolls back the associated change. Login timestamps bind to the beginning of authentication, but are not sufficient for password-change races. The credential binding additionally ties every token to the password-hash snapshot actually verified.
- Interpret naive stored dates as UTC; accept typed PostgreSQL and ISO SQLite dates. Do not infer epoch timestamps using the host local timezone.
- WebSocket authorization uses the same checks at connection, before inbound actions and outbound frames, and at one-second idle intervals. A request already authorized before a revocation commits is not retroactively rolled back. Direct SQL authority edits outside the provided mutators must write revocation state too if old tokens must remain invalid after authority is restored.
- Legacy NULL `is_active` values retain prior compatibility and are treated as active; explicit false/0 is rejected. This does not certify legacy account hygiene. No migration or production data change is included.
- Support requires an active, unexpired, consumed request bound to its tenant, target, approver and current active Admin operator. Operator/target revocation since request creation invalidates it. End/revoke/expire immediately denies subsequent requests. Conditional updates prevent launch races and state resurrection.
- `full_view` now means the reviewed passive-read allowlist: GET auth/me, dashboard summary/overview, cases/list/detail/activity, profile, team and staff; POST support-access/end is the sole allowed control action. Other endpoints, mutations and live-browser WebSockets are denied. Each allowed request records the actual operator and request/tenant/path, without citizen payloads. Ending support does not revoke the owner's normal login.
- Existing Admin visuals and aspirant layout remain unchanged apart from support-banner wording that explicitly explains read-only restrictions. This is intentionally not full owner impersonation; ancillary dashboard tools can return 403 for support sessions.

## F02 password-change/login race correction (2026-10-13)

The independent review of `3c254cd9` reproduced a remaining race for both login paths: the password transaction records a cutoff before commit; another login can read the old committed hash but receive a later `iat`. That stale token survived the committed password change. The earlier claim that login-start timestamps alone close the race was incomplete.

Correction: token issuers require the exact credential snapshot, emit `credential_state` as a domain-separated SHA-256 digest of username and bcrypt hash, and shared HTTP/WS validation compares it in constant time with the current user row. The JWT signature authenticates the digest; the password hash is never exposed. A stale login keeps the old binding even if token creation happens after commit. Changing the hash atomically changes the accepted binding, independent of timestamps. Rollback leaves the old hash and authority intact. Forced-reset tokens bind to the hash that reset wrote; support capabilities bind both target and operator credentials. Missing or unverifiable state fails closed. Existing suspension/tenant/role/cutoff/scope checks remain in force.

No schema migration, new auth store, extra database round trip or extra bcrypt verification is introduced. Normal request overhead is a SHA-256 digest over the existing user row and a constant-time comparison. All password writers automatically change this binding when they replace the bcrypt hash.

Rollout: update all normal and government-live backend workers together before relying on the invariant. All pre-binding JWTs must sign in again, including otherwise unexpired tokens. Existing support requests may need to be ended/revoked and approved anew. Do not accept unbound tokens for compatibility. No production credentials/data or deployment were changed here; in-flight requests already authorized before commit are not retroactively undone.

Deterministic regression coverage: PostgreSQL barriers hold the real password-change transaction after its revocation insert and let one or three real login requests verify old credentials before commit, for both Aspirant and Admin. After commit, all stale tokens and original tokens return 401; old-password login fails and new-password login works. No timing sleeps or mocked password checks are used. Additional tests cover transaction rollback for both roles, closing an open WebSocket after password change, missing credential state and support-operator credential changes. Existing support concurrency/revocation and tenant-authority tests remain intact.

Local security verification: **44 passed on PostgreSQL 14**, Python 3.14, `TZ=Asia/Kolkata`, distinct signing keys. PostgreSQL 17/Python 3.11 evidence will come from the existing dedicated CI job on the correction commit. Full-suite/build results and exact publication status are recorded in the PR update.
